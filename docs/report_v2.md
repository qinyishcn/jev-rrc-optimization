# Jev 类 Decider 在紧时延 RRC 配置上的扩展实验

2026-09-29。承接[第一版报告](report.md)。本报告比较真实 Decider 2B v11、Qwen3.5-2B-Base、传统配置规则与 Decider 领域适配；业务结果来自**明确假设下的 LTE 合成周期接收队列**，不是空口、UE 功耗或 5G NR DRX 实测。本文报告可复核的负面结果，不以弱固定配置衬托模型收益。

## 时间尺度、频率与计算开销

最终测试集共有 90 个独立合成场景，工业周期控制、交互 XR、游戏各 30 个。每条场景包含业务参数和固定随机种子，代表**一段 1000 ms 的分组到达时间窗**，有 30–3000 个包。Decider 在仿真前对每条场景**推理 1 次**，在这一秒内不逐包、不定期重新推理；故这里没有“每秒 1000 次”之类的在线推理频率。若把各个互相独立的 1 秒场景串起来，仅相当于每秒 1 次配置选择，但实际实验并未运行连续闭环。Qwen 与领域适配实验也按每条场景一次决策对齐。模型决策墙钟时间未加入包级时延；若要业务建立后或运行中变更配置，需要另测 RRC 生效时延和切换损失。

同一场景先生成同一条到达轨迹，对 `off`、`10/8`、`10/4`、`10/2`、`20/8`、`20/4`、`32/8`、`40/4`、`80/4` 共 9 个配置各执行一次离散事件仿真，然后所有策略复用对应结果。每条场景模拟的**业务时间为 1000 ms**，末尾未完成的队列继续排空。独立重新计时 3 次，生成到达轨迹加评估全部 9 个配置的 CPU 墙钟中位数，再跨 90 场景取中位数为 **2.56 ms**；这只是本机软件执行速度，不是物理系统运行 1 秒的测量。Decider 90 次预热后单请求 GPU 墙钟中位数 **186.24 ms**、P95 **216.83 ms**，RTX 3070 8GB、BF16、PyTorch eager；逐条数据的输入包数、推理耗时和仿真计时在[逐场景 CSV](../artifacts/temperature/per_scenario_timing.csv)。

| 场景类型（每类 30 条） | 每条场景推理次数 | 每条到达轨迹 | 九配置仿真 CPU 墙钟中位数 | Decider 推理墙钟中位数 |
|---|---:|---:|---:|---:|
| 工业周期控制 | 1 | 1000 ms | 3.17 ms | 187.88 ms |
| 交互 XR | 1 | 1000 ms | 3.70 ms | 183.43 ms |
| 游戏 | 1 | 1000 ms | 1.62 ms | 191.90 ms |

## 具体输入、配置和全部指标

[固定工业控制样例](example_v2.md)完整列出 UID `26092902-industrial_control-0000` 的实际 `state`、`question`、打乱后的 9 个 `options`，解释每个字段和配置片段，给出逐配置概率及全部策略的均值/P95/P99/最大包时延、超时包数、占空比、容量、负载、末端排空时间。本例期限 5 ms，每 4 ms 有 2 包，基准固定时延 3.4031 ms；Decider 的 `10/4` 在 500 包中有 241 包超时，占空比代理 40%；确定性规则和 Decider 风险筛选都选 `off`，0 包超时，占空比代理 100%。本例是约束与占空比的取舍示例，不代表总体增益。

## 已有传统配置与 Decider 结果

每场景允许至多 1% 的包超时。表中“超标场景”统计该约束失效的场景数；P99 是 90 个**场景级** P99 的算术均值；接收占空比只是 `onDuration/cycle` 的配置代理。

| 方法 | 超标场景 | 平均超时包比例 | 平均接收占空比 | 场景 P99 均值 |
|---|---:|---:|---:|---:|
| DRX 关闭 | 0/90 | 0% | 100% | 3.745 ms |
| 固定低时延 `10/8` | 2/90 | 0.135% | 80% | 5.306 ms |
| 校准集按业务固定 | 0/90 | 0% | 66.67% | 6.743 ms |
| 确定性自适应规则 `guard_only` | 0/90 | 0% | 54.67% | 7.773 ms |
| Decider 原始最大概率 | 36/90 | 19.198% | 46.56% | 14.363 ms |
| Decider + 相同风险筛选 | 0/90 | 0% | 69.56% | 6.639 ms |
| Decider Choice 温度 1.5（只改概率） | 36/90 | 19.198% | 46.56% | 14.363 ms |
| Decider 温度 1.5 + 置信度回退 | 0/90 | 0% | 54.67% | 7.773 ms |
| Decider 领域 LoRA 原始最大概率 | 10/90 | 4.333% | 57.78% | 7.358 ms |
| Decider 领域 LoRA + 相同风险筛选 | 0/90 | 0% | 66.89% | 6.564 ms |
| 事后最优，仅作离线上界 | 0/90 | 0.034% | 47.56% | 7.999 ms |

筛选后 Decider 虽零超标，却比不使用模型的 `guard_only` **多 14.89 个百分点**接收占空比。在当前目标和仿真条件下，它没有证明优于强传统方法；筛选器带来的合规不能归功于 Decider。更多基线、分业务分解与置信区间见[第一版报告](report.md)。

## Choice 温度与置信度回退

Decider 官方配置中的 Choice 温度为 1.164。新增 90 个校准场景的真实 Decider Choice 推理，使用校准集事后最低占空比可行配置作为标签，在 `0.5, 0.75, 1.0, 1.164, 1.5, 2, 3, 4` 网格中选择负对数似然最低的温度 **1.5**：从 1.164 的 **2.0532** 降至 **2.0351**。Choice 的所有候选 logit 被同一个正温度缩放，最高概率选项不变，因此**单独调温度时原始配置及仿真指标完全不变**：仍是 36/90 超标、46.56% 占空比。概率可用于后续阈值策略，但不能把 NLL 下降说成 RRC KPI 改善。

以温度 1.5 的概率在校准集上选“低置信度或原始选项未通过风险筛选时退回 `guard_only`”的阈值，要求校准集零超标，按最低平均占空比挑得阈值 **0.35**。在复用测试集上得到 **0/90 超标、54.67% 占空比、7.773 ms 场景 P99 均值**，逐条选择与 `guard_only` 相同。因此这个温度加门控方案也没有带来模型的可识别增益。[温度分析原始结果](../artifacts/temperature/analysis.json)记录整个网格和每条测试选择；校准和测试标签严格分开，但测试集在第一版已经公开，不把这次分析称为全新盲测。

## Qwen3.5-2B-Base 自回归对照

实际加载[Qwen 官方 Qwen3.5-2B-Base](https://huggingface.co/Qwen/Qwen3.5-2B-Base)固定 revision `b1485b2fa6dfa1287294f269f5fb618e03d52d7c`、SHA256 `928acbf11878c32185bbd863514d191769285065ab9ea14fbfe431303f5fdf2d`。在相同的 90 场景中，它看到相同业务描述和九个配置名，另有三个独立校准场景的示例答案；对每条场景自回归生成最多 16 个 token、贪心解码、到换行停止。**90/90 均生成单一合法配置**，没有隐藏无效输出或规则回退。[完整提示词、解析约束、逐条输出和复现方式](qwen_baseline.md)。

| 比较方法，同一批 90 条场景 | 推理中位数 / P95 | 超标场景 | 平均超时包比例 | 接收占空比 | 场景 P99 均值 |
|---|---:|---:|---:|---:|---:|
| Qwen Base 原始生成 | 1188.50 / 1238.51 ms | 48/90 | 26.84% | 33.67% | 90.727 ms |
| Decider 原始 Choice | 186.24 / 216.83 ms | 36/90 | 19.20% | 46.56% | 14.363 ms |
| Qwen + 同一单选工程回退 | 1188.50 / 1238.51 ms | 0/90 | 0% | 58.89% | 7.872 ms |
| Decider + 同一单选工程回退 | 186.24 / 216.83 ms | 0/90 | 0% | 66.44% | 7.008 ms |
| 无模型工程规则 | 0 / 0 ms | 0/90 | 0% | 54.67% | 7.773 ms |

原始 Qwen 比 Decider 多 **12/90** 个超标场景，配对 bootstrap 的 95% 区间为 **2.22–24.44 个百分点**；Decider 决策墙钟中位数在这套实现中快 **6.38 倍**。Qwen 的占空比更低，不能只挑超标率说其性能全面落后。两模型给出单一候选，再用同一描述符风险筛选处理不合格候选时，两者都零超标，但 Qwen 占空比 58.89% 低于 Decider 的 66.44%，最强无模型规则仍为 54.67%。此处“同一单选工程回退”与表中第一版的“在全部合格选项里按 Decider 概率重排”定义不同，已经分开命名。Qwen 官方注明 Base 是**仅预训练**、主要用于微调与上下文学习；Decider 由该底座经决策任务训练，提示词长度和解码过程也不同。因此这些结果只能说明所测**方法组合**的时延与效果，不能归结为两种架构在等训练条件下的内在优劣；两种模型原始输出均不能单独满足紧时延约束。

## Decider 领域微调

用新生成的 300 个训练描述符（工业/XR/游戏各 100）微调 Decider；每条描述符在三个独立流量相位下评估九种候选，要求三个相位各自的超时包比例不超过 1%，再以最低占空比生成监督标签。独立验证集 90 条，不含复用测试种子；实际更新的是 12 个注意力投影的 rank-4、alpha-8 LoRA，共 **208,896** 个参数，BF16 RTX 3070 上训练 **377.4 秒**、峰值分配显存 **3.98 GB**。模型权重冻结，适配器文件 838,192 字节、SHA256 `9b82de92e67d5fc20ede0c60d4844867b00b0533ca7071d30d93a3e962927c84`，不在公开仓库分发。验证集交叉熵从 **1.954 降至 1.117**。训练与验证只证明拟合合成标签，业务指标须另看配对评估。[训练和复现细节](decider_adaptation.md)。

在与第一版相同的 90 条场景上，适配后的原始选择从 **36/90 超标降至 10/90**，平均超时包比例从 **19.20% 降至 4.33%**，场景 P99 均值从 **14.363 降至 7.358 ms**；但其平均接收占空比由 **46.56% 增至 57.78%**，仍达不到零超标约束。加同一个工程筛选后为 **0/90 超标、66.89% 占空比、6.564 ms 场景 P99 均值**。它比未适配筛选版的 69.56% 占空比略低，但配对 bootstrap 的 95% 区间覆盖零；比 `guard_only` 的 **54.67%** 仍高 12.22 个百分点。这 90 条结果先前已在第一版公开，不能称为全新盲测。

适配器和规则冻结后，再用**从未用于训练、验证或阈值选择的新种子** `26093013` 生成工业/XR/游戏各 30 条确认场景。未适配 Decider 原始选择 **47/90 超标、46.56% 占空比、14.639 ms 场景 P99 均值**；适配版原始选择 **11/90 超标、59.78% 占空比、8.294 ms**；`guard_only` **0/90 超标、56.44% 占空比、7.524 ms**。同场景配对的超标率下降为 **40.00 个百分点**，场景 bootstrap 95% 区间 **31.11–48.89 个百分点**，但适配版相对未适配版多使用 **13.22 个百分点**占空比。给两版模型加入**同一个已冻结的工程筛选**后，二者均为 **0/90 超标、69.11% 占空比**；适配版场景 P99 均值从 6.593 降到 6.258 ms，配对差异的 95% 区间跨零。`guard_only` 仍以 56.44% 占空比零超标，低于两版筛选模型 **12.67 个百分点**。故当前证据支持“特定合成任务训练能纠正一部分 Decider 原始选择”，**不支持“模型优于最强无模型规则”**。确认集结果和逐条模型输出在 [`artifacts/adaptation/fresh_*`](../artifacts/adaptation/fresh_summary.json)。

同一新种子上，未适配 Decider 单次推理中位数 **200.89 ms**，适配版 **205.41 ms**；增加 LoRA 没有使推理更快。这个墙钟比较受同机后台负载影响，因而只报告为该环境的实测，不推断架构层面的普遍时延差异。

## 当前证据的边界与下一步

[分阶段验证方案](next_validation.md)梳理了 srsRAN Project 的公开 NR DRX 配置支持、Linux/核心网/UE/射频门槛、固定配置到运行时控制的验证路径、5G-LENA 适用边界，以及如何采集同条件包时延、配置失败与真实 UE 电流。公开 EEzim/RRC 数据只有 16 条协议 QA，没有 DRX 配置干预下的成对时延/能耗；当前合成队列没有 MAC 调度、HARQ、无线信道、多个 UE、完整 Active Time 或真实电池电流。只有在实际系统上对相同业务与无线条件做成对盲测，并相对 `guard_only` 等最强可部署基线满足时延约束且测得显著能耗改善，才能说这个 idea 有实际增益。
